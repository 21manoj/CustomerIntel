## Read this first: a live cross-tenant leak, found under item 8

Every tenant's own onboarding-created admin user currently has **unrestricted access to every other tenant's data** through the session-authenticated UI (`/app/api/*`), not just its own:

- `create_customer()` gives every new tenant's first user `role='admin'` (`mcp_server/cs_pulse_onboarding.py:200-205`) — this is meant as "this tenant's administrator."
- `app_api/auth.py`'s RBAC treats `role='admin'` as "platform superuser, no tenant restriction" (`user_scope()`, `:226-229`): `if user.role == 'admin': return None, None`, and `None` means "any customer_id/account_id allowed."
- The two meanings collide. A test currently *asserts* the unrestricted behavior as correct (`tests/test_app_api_auth.py:185-191`): an admin user scoped to one tenant is asserted to pass `allows_customer(admin, 999)` for an arbitrary other tenant.
- Net effect: any CSM-facing admin — created automatically at signup, no special provisioning — can pass a different `customer_id` to `/app/api/portfolio`, `/app/api/roi`, `/app/api/calibrations`, `/app/api/interventions/*/approve`, etc., and act on another tenant's data.

This is a targeted, small fix (distinguish "tenant admin" from "platform superuser" — a new role or a scoping flag, one column, a handful of call sites), separable from the much larger central-scoping refactor in item 8 below. Recommend pulling it forward and fixing it on its own, ahead of everything else on this list, regardless of what order the rest goes in.

## Recommended order

1. **Fix the admin/tenant-scoping leak** (pulled out of #8) — small, and it's a live bug, not backlog.
2. **`data_origin` loose ends** (#3) and **data-handling statement** (#6) — trivial, no dependencies, can happen anytime, useful to have written down regardless of sequencing.
3. **Review decisions bound to key_id** (#5) — reuses the already-proven `current_actor()` pattern; do this before #1 so the stamping bundle has a real actor-identity story to build on.
4. **LLM budget enforcement** (#4) — wiring existing machinery into two call sites; bounded and testable.
5. **Stamping bundle** (#1) — builds on #4/#5's actor and version groundwork; add `prompt_version`, extend `ContextNode.confidence` writes, define the shared `methodology` shape.
6. **Extraction eval second pass** (#7) — rerun now that the pipeline the scorecard was measuring has moved; add a comparable-run format.
7. **Risk dashboard** (#9) — do after #4/#5 so there's real budget/actor data worth surfacing, not empty tables.
8. **Journey snapshots** (#2) — the bigger data-model change; needs a retention-policy decision first.
9. **Central tenant scoping, full refactor** (#8, minus the leak already fixed in step 1) — the broadest item, last by design; consolidating ~93 call sites behind one helper is safest done last, once every other item's write paths have settled.
